# 발음 분석 결과 UI/UX 명세

작성일: 2026-09-18. 상태: 구현 전 제안 명세.

## 1. 목적과 기준

사용자가 결과 화면에서 “이번 녹음에서 무엇을 확인하고, 어떻게 연습할지”를 이해하도록 한다. 근거의 유무와 평가 범위를 정확히 표현하며, 숫자만으로 발음 오류를 확정하지 않는다.

API 기준은 [RunPod 발음 피드백 실측 목록](runpod-pronunciation-feedback-inventory-20260918.md)이다. 이 문서는 해당 조사 시점의 계약을 대상으로 한다. 이후 파이프라인 변경이나 설계 문서를 현재 구현으로 간주하지 않는다. 실제 VC-FE 화면·컴포넌트는 이번 작성에서 조사하지 않았으며 아래 배치는 신규 제안이다.

- 기본 대상: 모바일에서 녹음 후 발음 코칭을 확인하는 한국어 사용자.
- 기존 공개 API를 소비하는 UI 명세이며 신규 채점·LLM 생성 기능은 포함하지 않는다.
- 운영 응답의 scoreBreakdown/scoreHierarchy는 조사 시점의 로컬 BE HEAD와 다르다. 프론트 구현 전 목표 환경의 실제 응답 타입을 확인한다.
- 아래 카피·수치는 화면 설명용 예시다. 실측 결과·고정 생성 문구가 아니다.

## 2. 정보 구조와 화면 배치

결과는 하나의 페이지에서 아래 순서로 제공한다. 핵심 코칭은 기본 펼침, 세부 근거는 사용자가 요청할 때 펼친다.

| 순서 | 영역 | 기본 상태 | 사용자 질문 |
|---|---|---|---|
| 1 | 연습 문장·완료 시각·결과 상태 | 표시 | 어느 녹음의 결과인가? |
| 2 | 이번 연습 포인트 | 코칭 본문 펼침 | 무엇을 연습할까? |
| 3 | 분석 점수 | 총점과 짧은 설명 표시 | 이번 분석은 어떤 수준인가? |
| 4 | 발음 종류별 결과 | 대분류 목록 표시, 음소별 상세 접힘 | 어떤 소리를 살펴볼까? |
| 5 | 영상 관측 | 관측이 있을 때 요약 표시, 상세 접힘 | 영상으로 확인한 정보가 있나? |
| 6 | 다음 행동 | 다시 연습 / 목록으로 | 다음에 무엇을 할까? |

모바일 구조 예시:

```text
발음 분석 결과                     [목록으로]
연습 문장 · 분석 완료 시각

이번 연습 포인트
[확인할 소리: ㅇ]  [구간 듣기 — 가능한 경우]
발음 코칭 본문 …

분석 점수                       75 / 100
이번 녹음의 음성 분석 근거를 바탕으로 계산한 점수예요.
[점수 해석 보기]

발음 종류별 결과
모음             분석 근거 등급 3/4       [펼치기]
비음             분석 근거 등급 2/4       [펼치기]
…
대본과 음성의 대응 범위                   [펼치기]

영상 관측 · 점수에 포함되지 않아요        [펼치기]

[같은 문장 다시 연습]        [다른 문장 선택]
```

레이아웃 제안: 768px 미만은 단일 열, 이상은 코칭/점수 요약 2열과 전체 폭 상세 영역을 사용한다. 읽기 순서는 DOM에서도 동일하게 유지한다. 본문 최대 폭 1120px, 모바일 좌우 여백 16px, 영역 간 간격 24px를 초기값으로 하되 기존 디자인 토큰이 있으면 그 체계를 우선한다. 40개 음소를 첫 화면에 한꺼번에 펼치지 않는다.

## 3. 항목별 표시 명세

### 3.1 서술형 발음 코칭

- 데이터: `data.summaryFeedback`.
- 제목: “이번 연습 포인트”. `selectedPhone`이 있으면 별도 보조 배지 “확인할 소리: ㅇ”.
- 본문은 받은 문자열을 일반 텍스트로 렌더링하고 줄바꿈을 보존한다. HTML·Markdown을 실행하지 않는다.
- 본문에서 문장을 임의 분류해 “장점”, “오류”, “연습법”으로 재구성하지 않는다. 현재 응답은 구조화된 코칭 항목이 아니다.
- 길이가 긴 경우 기본 600자까지 문자 경계에서 미리보기와 “전체 피드백 보기”를 제공한다. 펼친 뒤 접더라도 키보드 포커스를 유지한다.
- 보조 설명: “분석에서 선택한 소리를 중심으로 한 연습 안내예요.”
- `null`/빈 문자열이면 outcome에 맞는 상태 문구를 사용한다. 점수로부터 조언을 자동 생성하지 않는다.
- 생성 경로 필드가 없으므로 “CLOVA 생성 완료”, “실시간 AI 답변” 등의 배지를 붙이지 않는다.
- 기존 regenerate는 저장된 문구 재사용이므로 “새로운 조언 받기” 버튼을 배치하지 않는다.

### 3.2 종합 점수

- 데이터: `data.overallScore`.
- 제목 “분석 점수”, 값 “75 / 100”. 소수부가 있으면 최대 한 자리 표시한다.
- 정수 0은 유효한 점수다. null/undefined는 “점수 정보 없음”으로 구분한다.
- 보조 설명: “이번 녹음의 음성 분석 근거를 바탕으로 계산한 점수예요.”
- “발음 정확도 75%”, “상위 25%”, “합격/불합격”, 임의의 우수/위험 등급을 추가하지 않는다.
- 단일 수치와 짧은 설명을 우선한다. 원형 게이지는 필수 요소가 아니며 숫자를 중복해서 강조하지 않는다.
- “점수 해석 보기”에서 적용된 발음 종류만 점수에 반영하며 영상 관측은 제외됨을 설명한다.
- 과거 결과와의 증감은 현재 계약만으로 제공하지 않는다. 향후 같은 기준표·문장·평가 조건의 비교 가능성을 확인한 후 별도 설계한다.

### 3.3 9개 대분류 평가

- 데이터: `data.scoreBreakdown.items[]`. ID로 매핑하고 label을 식별 키로 사용하지 않는다.
- API 순서를 유지한다: 모음 → 평음 파열음 → 경음 파열음 → 격음 파열음 → 마찰음 → 파찰음 → 비음 → 유음 → 기대 음소 대응 범위.
- 행에는 이름, 대상 소리 예시, “분석 근거 등급 3/4”, 펼침 버튼을 표시한다.
- 펼침에는 description, sampleCount, 해당 음소별 결과와 “배점 반영 7.5 / 10”을 표시한다. 가중 배점을 100점 만점의 독립 점수처럼 표현하지 않는다.
- 등급은 중립색 5단계 표시와 숫자를 함께 사용한다. 아래 표현은 원본 기준의 의미를 사용자용으로 요약한 것이다.

| level | 사용자 문구 |
|---|---|
| 4 | 분석 근거가 매우 안정적이에요 |
| 3 | 대체로 안정적이며 일부 확인이 필요해요 |
| 2 | 일부 소리를 다시 확인해 보세요 |
| 1 | 확인할 지점이 여러 곳 있어요 |
| 0 | 안정적인 분석 근거가 부족해요 |

- `applicable=false`: “이번 문장에 없는 소리”와 대시 표시. 펼침 설명은 허용하지만 0점·실패색을 사용하지 않는다.
- 해당 음소 상세가 없으면 대분류 설명까지만 제공한다. 같은 그룹이 scoreHierarchy에도 있어도 대분류 카드를 중복 생성하지 않는다.
- 총점을 프론트에서 다시 계산하지 않는다. 반올림된 하위 점수 합으로 API 총점을 덮어쓰지 않는다.

### 3.4 40개 음소별 평가

- 데이터: `data.scoreHierarchy.groups[].items[]` 중 음성 그룹. 그룹 ID로 분기하고 영상 그룹과 혼합하지 않는다.
- 각 대분류 펼침 안에 음소 버튼 목록을 배치한다. 기본은 `SCORED` 항목만 표시하고 “문장에 없는 소리 N개 보기”로 나머지를 펼친다.
- 음소 버튼에는 label과 등급을 표시한다. 선택하면 같은 영역에 description, sampleCount, level, normalizedScore를 보여준다.
- normalizedScore는 “등급 환산 75 / 100”으로 표시한다. label은 제공된 값을 사용하고 초성·종성 위치를 추측하지 않는다.
- 정렬 후보의 상세 설명은 API description을 표시한다. “누락 후보”를 “사용자가 생략함”으로 바꾸지 않는다.
- sampleCount는 “분석 대상 5개”로 표현한다. 여러 시도의 성공 횟수나 반복 연습 횟수가 아니다.
- 전체 결과 상단에서 음소를 선택하면 해당 그룹을 펼치고 항목으로 스크롤·포커스 이동한다. 음소 선택 자체가 새 API 분석을 발생시키지 않는다.

### 3.5 관심 항목

- 데이터: 음소별 `attention=true`.
- 해당 음소에 “먼저 살펴보기” 배지를 표시한다. 색상만으로 구분하지 않는다.
- 요약에 표시할 때는 API 순서로 최대 3개를 보여준다. 별도 순위 정보가 없으므로 1위/가장 심각한 오류 등으로 표현하지 않는다.
- `pronunciationEvidence`의 선택 음소와 관심 항목은 서로 다른 개념이다. 관심 항목을 선택 음소의 시간 구간에 연결하거나 새로운 코칭 문구를 만들지 않는다.
- 관심 항목이 없으면 영역을 숨긴다. “문제가 없다”는 문구를 자동 표시하지 않는다.

### 3.6 전체 기대 음소 대응 범위

- 데이터: `coverage` 그룹 및 `coverage.aligned` 항목.
- 제목 “대본과 음성의 대응 범위”. 발음 종류 목록의 마지막에 별도 구분선으로 배치한다.
- 설명: “대본에서 기대한 소리와 녹음 속 소리를 얼마나 대응시킬 수 있었는지 나타내요.”
- 등급과 API 설명을 표시한다. 발화한 단어 비율·대본 완독률·발음 정확도로 바꾸지 않는다.

### 3.7 선택 음소와 시간 구간

- 데이터: `pronunciationEvidence.selectedPhone/selectedExpectedIndex/selectedStartMs/selectedEndMs`.
- 코칭 카드 안에 선택 음소를 표시한다. selectedExpectedIndex는 기대 음소열의 index이므로 문자열의 글자 index로 사용하지 않는다.
- 현재 계약만으로 문장 속 특정 글자에 밑줄을 긋거나 모든 오류 위치를 색칠하지 않는다. 문자/음소 매핑 계약이 확보된 경우에만 추가한다.
- “구간 듣기” 노출 조건: 두 시각이 유효하고 `0 <= start < end <= mediaDuration`, 재생 가능한 권한 있는 녹음, 분석 오디오와 재생 매체의 시간축 일치가 확인됨.
- 버튼은 구간을 재생하고 종료 시 멈춘다. 반복은 별도 토글로 사용자가 선택한다. 자동 재생하지 않는다.
- 매체 접근·시간축은 현재 결과 API만으로 보장되지 않는다. 조건이 확인되지 않으면 재생 버튼을 숨기고 “이 소리의 재생 구간은 제공되지 않았어요”를 표시한다.
- 검출 점수·threshold·해시·내부 index는 일반 사용자 화면에 노출하지 않는다. 필요 시 별도 개발 진단 화면에서 취급한다.

### 3.8 영상 보조 근거

- 데이터: `visualSupplement`과 계층표의 영상 관측. 영역 제목 “영상 관측”, 보조 문구 “발음 점수에 포함되지 않아요”.
- 식별자 approvedClaimId, rendererKey, hash를 사용자 문구로 출력하지 않는다. 현재 알려진 ID별 승인 카피 목록이 확보되지 않았으므로 임의 조음 명령으로 번역하지 않는다.
- 이번 구현 범위에서는 API가 제공하는 관측 설명과 수치만 표시한다. 향후 승인된 renderer 매핑을 구현할 경우 별도 계약·테스트가 필요하다.
- 영상 입력 여부를 이미 알고 있고 결과가 null이면 “이번 분석에서 표시할 영상 관측이 없어요”. 원인을 조명·얼굴 가림·업로드 실패라고 추정하지 않는다.
- 입력 여부도 알 수 없고 관측이 없으면 영상 영역을 숨긴다. 업로드한 영상이 있었다는 가정을 하지 않는다.
- visualSupplement와 scoreHierarchy 중 하나만 있는 과거 응답도 처리한다. 계층표에 실제 관측이 있으면 visualSupplement null 여부만으로 해당 관측을 지우지 않는다.

### 3.9 입술 형상 관측

- 대상: 안쪽 벌림, 바깥쪽 벌림, 안쪽 개구 면적, 바깥 윤곽 면적.
- 원천은 `scoreHierarchy`의 `lip_shape` 그룹을 우선한다. closedBetaLipObservation 원본을 임의 파싱해 동일 카드를 중복 생성하지 않는다.
- 유효한 observation이 있는 항목만 기본 표시한다. label + 값 + 도움말 + “관측값 · 평가 기준 미검증” 배지를 제공한다.
- ratio는 비율 값 그대로 최대 소수 셋째 자리까지 표시한다. 값이 0보다 크지만 반올림하면 0이면 “0.001 미만”. 퍼센트나 mm로 환산하지 않는다.
- 예: “안쪽 벌림 0.180 — 입 너비에 대한 비율”. 표시는 원본을 변경하지 않는다.
- 시간 구간이 있으면 “관측 구간 0.82–0.96초”. 이 구간을 영상 재생에 적용하려면 영상의 동일 시간축이 별도로 확인되어야 한다.
- 좋음/나쁨 색상, 이상적인 범위, 점수 막대, 사용자 평균 비교를 사용하지 않는다. 현재 검증된 기준이 없다.

### 3.10 입술 움직임 항목

- 대상: 닫힘 정도, 열림 전환, 닫힘 전환, 움직임 변화율 패턴.
- 현재 실제 값이 없으므로 기본 화면에는 빈 카드 4개를 나열하지 않는다.
- “영상 분석 범위 보기” 안에서 “입술 움직임 평가는 현재 제공되지 않아요” 한 줄로 요약한다.
- `UNAVAILABLE`는 요청 실패를 뜻하지 않는다. 영상 분석을 다시 실행하는 버튼이나 재업로드 안내를 자동 제공하지 않는다.

### 3.11 결과 상태

상태는 문자열 내용이 아닌 명시적인 status/outcome으로 판단한다.

| 조건 | 화면 | 행동 |
|---|---|---|
| COMPLETED + COACHING_READY | “분석이 완료됐어요”, 코칭·유효한 점수 표시 | 같은 문장 다시 연습 / 다른 문장 선택 |
| COMPLETED + COMPLETED_NO_ISSUE | “이번 분석에서는 우선 안내할 교정 지점이 선택되지 않았어요” | 유효한 점수는 유지, 다른 문장 선택 가능 |
| COMPLETED + outcome 없음/알 수 없음 | “분석이 완료됐어요”, 유효한 필드만 표시 | 결과를 성공 코칭·완벽한 발음으로 추정하지 않음 |
| FAILED | 서버 실패 code에 대응하는 안내 | 실제 지원하는 재시도 동작만 제공 |
| PENDING / PROCESSING | 대기 화면 | 상태 polling 지속 |

COACHING_READY인데 본문이 비어 있으면 “코칭 문구가 제공되지 않았어요”와 유효한 점수·근거를 표시한다. 전체 분석을 실패로 바꾸지 않는다. COMPLETED_NO_ISSUE를 100점으로 덮어쓰지 않는다. 알 수 없는 상태값은 “분석 상태를 확인하고 있어요”와 조회 재시도 동작을 제공한다.

## 4. 로딩·오류·재시도 동작

| 상황 | 표시 및 동작 |
|---|---|
| 결과 요청 중 | 제목·카드 skeleton, 점수 자리에는 숫자 미표시 |
| 분석 진행 중 | “분석 중이에요. 완료되면 결과를 보여드릴게요.” 실제 단계 정보가 없으므로 단계 진행률·남은 초를 만들지 않음 |
| 대기 한도 도달 | “분석이 예상보다 오래 걸리고 있어요.” 기본 버튼 “분석 상태 다시 확인”. 기존 sessionId/analysisId로 조회하고 재업로드하지 않음 |
| COMPLETED 확인 후 상세 GET 실패 | “분석은 완료됐지만 결과를 불러오지 못했어요.” “결과 다시 불러오기”는 GET만 실행 |
| 일시적 네트워크 오류 | 기존 결과가 있으면 유지하며 상단 안내. 자동 조회 재시도는 기존 클라이언트 정책 적용 |
| 인증 만료 | 기존 인증 갱신 흐름을 먼저 사용. 실패 시 로그인 안내, 비밀정보 없는 결과 식별자로 복귀 맥락 유지 |
| 권한 없음/대상 없음 | “이 결과를 확인할 수 없어요.” 목록 이동. 다른 사용자의 결과 존재 여부를 설명하지 않음 |
| 실제 분석 FAILED | 알려진 code별 원인과 가능한 다음 행동. 문자열의 '녹음' 포함 여부로 음질 오류를 추정하지 않음 |

대기 정책 제안은 최대 600초이며 이는 이번 명세의 목표값이다. 운영 FE에 반영됐다고 가정하지 않는다. 이미 수신한 COMPLETED/FAILED는 경과 시간 검사보다 먼저 처리한다. 조회 중복 실행을 막고 화면을 떠나면 조회를 정리한다. 상태 재조회·결과 재조회·분석 재시도·다시 녹음은 별개 액션으로 구현한다.

“같은 문장 다시 연습”은 녹음 준비 화면으로 이동하는 행동이다. 사용자가 녹음·제출하기 전에 분석 API를 자동 호출하지 않는다. 실제 실패 재시도 endpoint와 멱등성은 FE 구현 시 현행 계약을 확인한다.

## 5. 데이터 표현·호환성

| 입력 | 처리 |
|---|---|
| 숫자 0 | 유효한 값으로 표시. truthy 검사 금지 |
| null/undefined | 정보 없음으로 처리. 0점으로 대체하지 않음 |
| scoreHierarchy 없음 | scoreBreakdown과 본문으로 결과 제공. 계층표 생성 금지 |
| scoreBreakdown 없음 | hierarchy가 있으면 그 그룹 사용. 없으면 총점·본문만 표시 |
| 두 점수표의 rubricRevision 불일치 | 총점·본문 유지, 세부 점수 영역은 “세부 점수 정보를 표시할 수 없어요”. 서로 다른 기준표를 합치지 않음 |
| 유효하지 않은 점수/등급/시각 | 해당 값 또는 동작만 숨기고 나머지 결과 유지. 범위 안으로 조용히 보정하지 않음 |
| 알 수 없는 그룹/상태 | 검증되지 않은 차트나 행동 생성 금지. 알려진 항목은 계속 표시 |
| 관측 상태 NOT_VALIDATED | 관측 설명과 값 표시, 점수/좋음·나쁨 판단 없음 |
| NOT_PROVIDED / UNAVAILABLE | 각각 “영상이 제공되지 않았어요” / “표시할 관측이 없어요”. 서버가 준 상태 범위에서만 설명 |

입력 검증 경계: overallScore 0~100, level 정수 0~4, normalizedScore 0~100, sampleCount 음이 아닌 정수, 유한 숫자. `score/maxScore`의 maxScore=0에는 비율 계산을 하지 않는다. API label/description은 일반 텍스트로만 렌더링한다.

현재 별도 STT 결과·억양·속도·강세·쉼·강점/약점·전체 음절 segments는 제공 대상으로 삼지 않는다. 비어 있는 카드와 가짜 그래프를 만들지 않는다. 49개 leaf를 “49가지 발음 평가 완료”라고 표현하지 않는다.

## 6. 접근성·반응형 요구사항

아래는 제품 구현의 수용 기준이며 특정 외부 인증 준수를 주장하는 문구가 아니다.

- 본문 기본 16px, 보조 문구 14px 이상, 줄 간격 1.5 이상. 320px 폭과 글자 확대 200%에서 가로 스크롤·내용 잘림을 만들지 않는다.
- 주요 터치 영역 44×44px 이상. 접힘 버튼에는 aria-expanded 및 제어 영역 연결을 제공한다.
- 등급·관심 항목·상태는 색상 외에 텍스트/아이콘으로도 구분한다. 일반 텍스트 대비 4.5:1 이상을 목표로 한다.
- 순서 있는 제목 구조, 키보드 포커스 표시, 논리적인 Tab 순서를 유지한다. 모달 도움말 사용 시 포커스를 가두고 닫은 뒤 실행 버튼으로 복귀한다.
- 점수 읽기 예: “분석 점수, 100점 만점에 75점”. 그래프가 있어도 동일 의미의 텍스트가 있어야 한다.
- 분석 완료·조회 오류만 polite live 영역에서 안내한다. polling 때마다 스크린리더에 반복 알리지 않는다.
- 미디어 자동 재생 금지. 음소 구간 재생 버튼은 “선택한 소리 ㅇ, 0.82초부터 0.96초까지 듣기”와 같은 접근 가능한 이름을 갖는다.
- 긴 코칭·한글 줄바꿈·다크모드·화면 회전·하단 안전 영역을 확인한다. 고정 하단 버튼이 본문이나 포커스를 덮지 않는다.

## 7. 구현 단위와 추가 계약 필요 여부

| 단위 | 현행 계약으로 구현 | 조건/추가 확인 |
|---|---|---|
| 코칭 카드·총점·대분류·음소 상세 | 가능 | 목표 환경의 응답 DTO 확인 |
| 관심 배지·대응 범위 설명 | 가능 | 명시적인 attention/ID 사용 |
| 영상 관측값 표시 | 조건부 가능 | 구조화된 관측 존재, 평가 문구와 분리 |
| 선택 구간 재생 | 조건부 | 권한 있는 재생 URL·보존 정책·동일 시간축 확인 필요 |
| 대본 글자별 오류 강조 | 현재 범위 제외 | 기대 음소 index와 원문 위치 매핑 필요 |
| 문제별 개별 코칭 카드 여러 개 | 현재 범위 제외 | 구조화된 복수 코칭 응답 필요 |
| fallback 여부 배지 | 현재 범위 제외 | 생성 경로의 공개 필드 필요 |
| 추이·이전 녹음 비교 | 현재 범위 제외 | 조회 API와 기준표 비교 가능성 필요 |

권장 컴포넌트 책임: ResultStatus, CoachingSummary, AnalysisScore, PronunciationGroupList, PhoneEvidenceDetail, VisualObservationPanel, ResultActions. 명칭은 제안이며 기존 FE 구조를 확인한 뒤 조정한다. API 응답 정규화·상태 판정은 화면 컴포넌트와 분리하고 수치 계산은 서버 책임을 유지한다.

## 8. 완료 조건과 검증 시나리오

아래는 향후 구현의 QA 기준이다. 이번 문서 작성에서 실제 FE 테스트를 실행했다는 의미는 아니다.

| 시나리오 | 수용 조건 |
|---|---|
| 일반 v3 COACHING_READY | 본문·총점·9개 기준·음소 상세가 연결되고 동일 데이터 중복 카드 없음 |
| 총점 0 / null | 각각 0점 / 정보 없음으로 구분 |
| 기대 음소 표본 0 | NOT_APPLICABLE로 표시, 실패·0점 아님 |
| attention 3개 | 배지와 해당 음소 이동, 순위나 별도 코칭 생성 없음 |
| 선택 음소와 관심 음소 불일치 | 시간 구간·본문을 다른 음소에 연결하지 않음 |
| 선택 구간 null 또는 시간축 미확인 | 재생 버튼 없음, 문장 위치를 임의 강조하지 않음 |
| 영상 관측 있음 | ratio와 미검증 표시, 총점에 합산하지 않음 |
| 영상 관측 없음 | 음성 결과 유지, 영상 오류를 전체 실패로 바꾸지 않음 |
| no issue | 중립 완료 문구, 만점·완벽 배지 없음 |
| 구버전 응답 | hierarchy 없이도 본문·점수 사용 가능 |
| 긴 문구·HTML 유사 문자열 | 안전한 일반 텍스트, 펼침/접힘·줄바꿈 정상 |
| 시간 한도 직전 COMPLETED 수신 | 완료 결과 표시, timeout 화면으로 되돌아가지 않음 |
| 상세 GET 실패·상태 재확인 | GET 재조회만 발생, 업로드·새 analyze 호출 없음 |
| 중복 클릭·화면 이탈 | 중복 조회·제출 방지, polling 정리 |
| 키보드·스크린리더·320px·200% 확대 | 주요 정보·버튼 접근 가능, 상태 중복 안내·가림 없음 |

구현 시 fixture 기반 컴포넌트 테스트와 위 상태 전이 통합 테스트를 우선한다. 새 사용자 미디어 전송·LLM 추론 없이도 UI 검증이 가능해야 한다. 사용자 코칭 본문·대본·미디어 URL을 분석용 이벤트 로그에 기록하지 않는다.

## 9. 이번 산출물과 제한

작성 범위는 UI/UX 명세 한 파일이다. 기존 조사 결과와 API 필드의 대응, null/미지원/구버전 처리, 링크·UTF-8·공백을 검토한다. 실제 FE 구현, 브라우저 검증, 추가 운영 실측, 추론·배포는 수행하지 않는다. 기존 사용자 문서와 코드 변경은 보존한다.
