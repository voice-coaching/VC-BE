# SpeakAI 프론트엔드 QA 엣지 케이스 테스트 계획서

## 1. 문서 목적

VC-FE의 문장 연습 기능을 대상으로 입력, 문장 분리, 녹음, 업로드, AI 분석, 결과 저장 및 재진입 흐름을 검증한다.

특히 다음과 같은 비정상 입력과 음성을 중점적으로 확인한다.

- 문장의 절반만 읽는 경우
- 한 글자만 읽는 경우
- 문장 중간 또는 끝의 글자를 누락하는 경우
- 사용자가 입력할 수 있는 최대 길이를 초과하는 원고
- 무음, 잡음, 권한 거부, 네트워크 중단

## 2. 작업 범위

## 3. 현재 구현에서 확인할 기준

- 사용자 원고 입력 제한은 `300자`이다.
- 화면 입력에는 `maxLength=300`이 적용되어 있다.
- 서버 전송 전 원고의 앞뒤 공백을 제거하고 연속 공백·줄바꿈을 하나의 공백으로 정규화한다.
- 문장은 `.`, `!`, `?` 및 한국어 전각 문장부호를 기준으로 분리한다.
- 녹음 최대 시간은 `60초`이다.
- 일반 연습과 Direct 분석은 서로 다른 화면 흐름을 사용할 수 있다.
- 업로드 URL이 인증 오류로 만료된 경우 새 URL을 받아 재시도하는 로직이 있다.

## 6. 문장 분리 테스트

다음 원고를 입력하고 미리보기 문장 수와 실제 연습 문장 목록을 비교한다.

```text
문장 하나. 문장 둘.
```

```text
문장 하나... 문장 둘.
```

```text
숫자 3.14를 입력합니다. 다음 문장입니다.
```

```text
"따옴표 안의 문장입니다." 다음 문장입니다.
```

```text
괄호 안 문장입니다. (추가 설명입니다.) 다음 문장입니다.
```

```text
문장 하나


문장 둘
```

확인 항목:

- 소수점이 문장 경계로 잘못 처리되지 않는가
- 말줄임표가 빈 문장을 만들지 않는가
- 따옴표·괄호 뒤 문장 분리가 자연스러운가
- 문장부호 없는 마지막 문장이 누락되지 않는가
- 미리보기의 문장 수와 녹음 화면의 문장 수가 같은가
- 서버에 전달된 원고와 화면에 표시된 원고가 의도대로 일치하는가

각 음성 샘플로 분석을 요청하고 다음을 확인한다.

- 분석 실패와 낮은 점수를 구분하는가
- 실패한 분석을 학습 완료로 기록하지 않는가
- 사용자가 다시 녹음할 수 있는가
- 결과 화면에서 어떤 문장이 문제였는지 확인 가능한가

## 9. 업로드 및 분석 흐름 테스트

1. 정상 녹음 후 업로드 URL 발급
2. S3 업로드 진행률 확인
3. 녹음 등록 및 녹음 목록 반영 확인
4. 선택 녹음 지정 확인
5. 분석 요청 후 진행 상태 확인
6. 분석 완료 후 결과 조회
7. 학습 완료 및 이력 반영 확인

다음 장애를 각각 재현한다.

- 업로드 URL 발급 중 네트워크 차단
- S3 PUT 중 네트워크 차단
- 만료된 presigned URL 사용
- 녹음 등록 API 409 응답
- 분석 API 409 또는 502 응답
- 분석 결과 조회 timeout
- 결과 저장 중 브라우저 새로고침
- 분석 버튼 연속 클릭

기대 결과:

- 만료된 업로드 URL은 새 URL로 한 번 재시도한다.
- 같은 분석 요청이 중복 생성되지 않는다.
- 분석 결과가 도착하기 전에 완료 처리되지 않는다.
- 새로고침 후 세션 또는 분석 상태를 복구할 수 있다.
- 재시도 가능한 오류와 재시도 불가능한 오류가 구분된다.

## 10. 1000자 원고 테스트

현재 화면 입력 제한이 300자라면 1000자는 UI에서 정상 입력할 수 없다. 따라서 다음 두 가지를 분리해 테스트한다.

### 프론트 UI 테스트

- 1000자 붙여넣기 시 300자에서 잘리는지 확인
- 잘린 사실을 사용자에게 표시하는지 확인
- 미리보기와 저장 요청의 원고가 동일한지 확인

### 백엔드 계약 테스트

```http
POST /api/practice-contents/custom
Authorization: Bearer <accessToken>
Content-Type: application/json
Idempotency-Key: qa-1000-character-test
```

```json
{
  "title": "QA 1000자 테스트",
  "scriptText": "1000자 원고",
  "learningFocus": "PRONUNCIATION",
  "retention": "SESSION_HISTORY",
  "locale": "ko-KR"
}
```

기대 결과는 명확해야 한다.

- 제한 정책이 300자라면 `400 Bad Request`
- 허용 정책이라면 콘텐츠 생성 후 긴 원고 연습 가능
- `500 Internal Server Error`가 발생하면 서버 예외
- 프론트가 원고를 임의로 잘라 전송하면 프론트 버그

## 12. 판정 기준

### Blocker

- 정상 녹음이 업로드되지 않음
- 다른 사용자의 세션 또는 결과가 노출됨
- 잘못된 음성이 정상 완료로 기록됨
- 결괏값 없이 학습 완료 처리됨

### High

- 부분 발화가 항상 정상 통과함
- 300자 제한을 우회하면 서버가 500을 반환함
- 새로고침 후 진행 중 분석을 복구할 수 없음
- 중복 클릭으로 콘텐츠·세션·분석이 중복 생성됨

### Medium

- 문장 수와 실제 연습 단계가 다름
- 글자 수 표시가 이모지·조합형 한글에서 부정확함
- 오류 메시지는 표시되지만 재시도 경로가 없음

### Low

- 진행률 또는 문장 번호 표시가 일시적으로 어긋남
- 특정 문장부호에서 미리보기 표현만 부자연스러움

## 16. 추가 QA 목표 및 준비

목표는 정상 플로우가 아니라 인증 경계, 상태 복구, 동시 요청, 데이터 격리, 브라우저 권한, 장애 복구를 검증하는 것이다.

준비 데이터:

- 테스트 계정 2개: `user-A`, `user-B`

`MEDIA-004`는 배포 사이트에서 사용자가 직접 실행할 수 있는 테스트가 아니다. 브라우저 화면에는 임의의 오디오 파일을 선택하는 `<input type="file">`가 없고, 녹음 결과가 `MediaRecorder` 또는 PCM 처리 결과로 생성된다. 따라서 수동 QA 결과에는 `N/A - UI 경로 없음`으로 기록하고, 다음 중 하나로 별도 검증한다.

- 백엔드 통합 테스트에서 잘못된 `Content-Type`, 빈 바디, 손상 파일을 업로드한다.
- Playwright/API 자동화에서 업로드 요청의 Blob MIME을 강제로 바꿔 프론트 오류 처리를 확인한다.
- presigned PUT 이후 등록 API에 허용되지 않은 object key 또는 파일 메타데이터를 보내 서버 거부를 확인한다.

반대로 다음 항목은 실제 배포 사이트에서 수동 실행할 수 있다.

- 마이크 권한 거부·재허용
- 무음·저음량·주변 소음 녹음
- 녹음 60초 경계와 자동 종료
- 녹음 중 통화·알림·백그라운드 전환
- 업로드·분석 중 네트워크 끊김

## 24. 추가 테스트 실행 순서

1. 테스트 계정 2개로 인증·데이터 격리 테스트를 먼저 수행한다.
2. 딥링크, 새로고침, 뒤로가기, 여러 탭으로 상태 복구를 검증한다.
3. 세션·업로드·분석·완료의 중복 클릭과 멱등성을 검증한다.
4. 파일·TTS·presigned URL의 경계와 만료를 검증한다.
5. API의 빈 응답, null, 알 수 없는 enum, 409/429/500/502를 주입해 확인한다.
6. XSS, 토큰 노출, 로그아웃 후 캐시 잔존 여부를 확인한다.
7. 느린 네트워크, 오프라인 전환, 권한 변경, 백그라운드 전환을 반복한다.
8. 마지막으로 키보드·스크린 리더·확대와 모바일 환경을 검증한다.

## 25. 추가 QA 합격 기준

- 노션 export의 24개 이슈와 별도로 위 테스트 ID를 추적할 수 있어야 한다.
- 인증 실패·네트워크 실패·분석 실패가 성공 상태로 저장되지 않아야 한다.
- 동일 사용자 요청은 중복 리소스를 만들지 않아야 한다.
- 사용자 간 세션·스크립트·오디오·분석 결과가 절대 섞이지 않아야 한다.
- 만료·재시도·복구 흐름에서 사용자가 다음 행동을 알 수 있어야 한다.
- 모든 Blocker/High 추가 테스트가 통과하거나 재현 절차와 영향도가 등록되어야 릴리즈 후보로 판정한다.
